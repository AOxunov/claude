Договорились: **код пишу я сам, Claude проверяет и объясняет ошибки**, а не пишет реализацию за меня.

## Что разобрали

### Баг: имя сеттера (исправлено)
`Employee.java` — было `setUpdated_by`, стало `setUpdatedBy`.
Jackson и Spring ищут методы по **JavaBean-конвенции**: поле `updatedBy` → `getUpdatedBy()` / `setUpdatedBy()`.
Если имя не совпадает — сеттер молча не находится, поле остаётся `null`, ошибки при этом нет.

### Безопасность: пароль БД (исправлено в коде, но не до конца)
Пароль от Neon лежал открытым текстом в `application.properties` и **был закоммичен в публичный репозиторий** на GitHub (коммит `b275bbb`, уже запушен в `origin/main`).
Заменили на плейсхолдер `${DB_PASSWORD}`.

### Переменные окружения — как работают
- Пара `ключ=значение`, живёт **в памяти процесса**, не в файле.
- Родительский процесс (IntelliJ) при запуске передаёт копию окружения дочернему (`java.exe`).
- Spring видит `${DB_PASSWORD}` в properties → лезет в окружение процесса (`System.getenv()`) → подставляет значение.
- Если переменной нет → приложение падает при старте (`password authentication failed`, SQLState `28P01`).
- Плюс: значение никогда не попадает в git; в проде задаётся на уровне ОС/Docker, а код одинаковый везде.

**Как задать в IntelliJ:** Run Configuration → **Modify options** (Alt+M) → выбрать **Environment variables** → появится поле → вписать `DB_PASSWORD=...` → Apply → OK.
(Поле по умолчанию скрыто — сразу его в форме не видно.)

### Чтение стектрейса
В логе ошибки главное — **самая нижняя** причина (`Caused by`), а не верхняя.
Тут: `Unable to determine Dialect` наверху — всего лишь следствие. Настоящая причина внизу: `password authentication failed for user 'neondb_owner'`.

### findById — написал сам, проверено ✅
```java
@GetMapping("/{id}")
public ResponseEntity<Employee> findById(@PathVariable UUID id) {
    Optional<Employee> employee = repository.findById(id);
    return employee.map(ResponseEntity::ok)
            .orElseGet(() -> ResponseEntity.notFound().build());
}
```
Проверено: 200 на существующий id, 404 на несуществующий.

Ключевые понятия:
- `@GetMapping("/{id}")` — `{id}` плейсхолдер в маршруте; `@PathVariable UUID id` вытаскивает его в параметр, Spring сам конвертирует строку → UUID (кривая строка → 400 автоматически).
- `findById()` возвращает `Optional<Employee>`, а не `Employee` — обёртка, заставляющая явно обработать «не найдено» вместо NPE.
- **`return` в контроллере = «отправь это клиенту как HTTP-ответ»**, а не обычный возврат значения. Jackson сам сериализует объект в JSON.
- Тип возврата `Employee` → статус всегда 200, отдать 404 физически некуда. Поэтому нужен `ResponseEntity<Employee>` — «тело + статус + заголовки».
- `.map()` — применить функцию к содержимому, если оно есть; `.orElseGet()` — распаковать, иначе вызвать функцию.
- `orElseGet` vs `orElse`: `orElse` вычисляет аргумент **всегда**, даже когда значение есть. `orElseGet` — лениво. Привычка на будущее.

## Что понял

- Имя метода в Java — часть контракта для фреймворков, а не просто стиль.
- Секреты в git остаются в истории навсегда, даже если убрать их из файла.
- HTTP-статус — это не то же самое, что возвращаемое значение метода; чтобы управлять статусом, нужен `ResponseEntity`.

### Следующая тема: DTO
Обсудили, зачем нужны — **на реальном баге в моём коде**:
```java
@PostMapping
public Employee save(@RequestBody Employee employee) { return repository.save(employee); }
```
1. Клиент присылает JSON прямо в Entity → может задать **любое** поле: `id`, `createdAt`, `createdBy`, `updateId`. Это **mass assignment**.
2. Так как `@Id` без `@GeneratedValue`, id приходит снаружи. Если клиент пришлёт **существующий** id — `save()` сделает не вставку, а **перезапись чужой записи**. Реальная дыра.
3. В ответ отдаётся вся Entity — наружу утекают `salary`, `state`, `updateId`.

Суть: **структура таблицы ≠ контракт API**. DTO — отдельные классы под контракт: `CreateEmployeeRequest` (что клиенту можно присылать) и `EmployeeResponse` (что можно показывать). Меняешь колонку в БД — API не ломается.

План: сначала `deleteById`, потом `EmployeeResponse` + переделать `findById` на него.

### Про поля status / timestamp / message в ответе
Спрашивал, нужны ли они, как в проде.
- `status` в теле — **не нужен**, дублирует HTTP-код. Наследие старых API.
- `timestamp` / `message` **для ошибок** — нужны, и в Spring это уже встроено: класс **`ProblemDetail`** (стандарт RFC 7807).
- Тема «обработка ошибок через `@ExceptionHandler` / `@ControllerAdvice` + `ProblemDetail`» — взять **после** DTO.
