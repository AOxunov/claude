# EasyTrip × RealPay: обзор интеграции

> Состояние на **2026-09-22**. Начинать отсюда — здесь суть, решения, текущее состояние
> и следующие шаги. Детали — в заметках ниже.

## Суть

- easy-trip — **агент** RealPay: регистрирует партнёров как мерчантов и сам обслуживает
  вызовы RealPay (callback-и) за каждого.
- Мерчанты — **объекты из `places`**: отели (`hotels`), рестораны (`meal_places`),
  магазины (`stores`).
- В каждом объекте висит QR easy-trip. Клиент сканирует его в **мобильном приложении
  easy-trip** → открывается инфо-окно объекта (уже сделано) → кнопка «Оплатить».
- Заказов/броней в проекте нет, сумму вводит клиент.
- Оплата идёт через **RealPay Flutter SDK** в приложении; RealPay при этом вызывает наши callback-и.

## Сервисы RealPay (stage)

| Сервис | Базовый URL | Схема OpenAPI | Используем |
|---|---|---|---|
| agent | `https://agent.stage.realpay.uz/api/agent` | `/api/agent/docs` | **да** — мерчанты, кассы, шаблоны касс |
| merchant-billing | `https://merchant-billing.stage.realpay.uz/api/merchant/billing` | `/api/merchant/billing/docs` | нет — аналог агента для аккаунтов MERCHANT_BILLING (через него работал edu); один шаблон на аккаунт |
| checkout SDK | `https://api-checkout.stage.realpay.uz/api/merchant/sdk` | `/api/merchant/sdk/api/docs` | **да** — оплата из приложения |

- Токен агента принимает и billing.
- Успешный `code` в ответах RealPay — **`0`** (не `200`, как в примерах PDF).
- Нет/битый токен → HTTP 200 с `code: -8`.

## Поток оплаты

| # | Запрос | Кто вызывает | Куда |
|---|---|---|---|
| 1 | `v1/real-pay/auth/sdk` → токен SDK | приложение (токен easy-trip) | easy-trip |
| 2 | `v1/real-pay/payment/create` `{place_id, amount}` → `{payment_id, kassa_id, amount}` | приложение (токен easy-trip) | easy-trip |
| 3 | `payment/v2/info/card-id` с `param_in_values: {"payment_id": …}` | приложение через SDK | RealPay |
| 4 | `callback/info` | RealPay | easy-trip |
| 5 | `payment/v2/payment/card-id` с SMS-кодом | приложение через SDK | RealPay |
| 6 | `callback/payment` (сначала `IN_PROGRESS`, потом `SUCCESS`/`ERROR`) | RealPay | easy-trip |

Позже RealPay может вызвать `check-status`, `cancel`, `reconciliation`.

## Ключевые решения и почему

1. **Схема с `payment_id`.** Платёж создаётся у нас до оплаты (`payment/create`), `user_id`
   берётся из токена easy-trip **на сервере**. В кассе одно поле — `payment_id`.
   *Почему:* данным из приложения (`user_id`, телефон, имя из сессии) доверять нельзя;
   сумма и объект фиксируются заранее; логика меняется у нас, а не в кассах.
2. **Шаблон кассы и мерчант — в агентском сервисе.** Касса копирует шаблон в момент
   создания; API изменения кассы нет. Сменить поля у действующих касс = новая касса +
   повторная активация RealPay для каждого мерчанта → поля кассы определить до подключения
   реальных объектов.
3. **Все callback-и работают с одной строкой `realpay_transaction`.** Статус берётся из БД.
   Переходы: `NEW → IN_PROGRESS/SUCCESS/ERROR`, `IN_PROGRESS → SUCCESS/ERROR`, назад нельзя.
   Отмена — только из `SUCCESS`, `state` при этом не трогаем.
4. **Сверка — по времени RealPay (`rp_time`)**, только строки с `transaction_id`.
5. **Basic-авторизацию callback-ов проверяет сама платформа** (настройка эндпоинта);
   логин/пароль должны совпадать с кассой. Без Basic → 401.
6. **Внешний адрес эндпоинтов easy-trip — `https://easy-trip.com/endpoint/api/<path>`.**
   Путь `/services/platon-core/api/...` отдаёт HTML фронта — для callback-ов не годится.
7. Ответ callback-а платформа заворачивает в свой конверт, наши поля — в `data`.
   `response_code` и `response_message` лежат там, где их ищет RealPay; в edu работало так же.

## До прода

- **`auth/sdk`: у каждого пользователя свой `client_id` RealPay.** Иначе сохранённые
  карты одного пользователя видны всем. Не проверено.
- **Пароли.** Касса создана с паролем, который раньше использовался в кассе edu, → для прода
  новый сложный пароль; в edu его сменить. Пароли и токены в заметки и git не писать.
- Скрипт токена агента: ключ Redis не должен совпадать с паролем; при `code: -8` сбрасывать
  кеш и входить заново; успех — `code: 0`; логин/пароль вынести из кода.
- Пути: `auth/sdk` и `payment/create` лежат на `v1/real-pay/…`, остальное — на
  `v1/stage/real-pay/…`. Привести к одной схеме stage/прод.
- Фискализация: ИКПУ и код упаковки по типам объектов, НДС, не дублирует ли чек RealPay
  чек самого объекта (особенно магазины).
- Скидки (`places.card_discount_percentage`, `discount` у ресторанов и магазинов) —
  применяются ли при оплате.
- Агентское вознаграждение easy-trip.
- Логирование Flutter SDK (печатает Bearer) выключить в релизе.
