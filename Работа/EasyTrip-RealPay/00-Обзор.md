# EasyTrip × RealPay: обзор интеграции

EasyTrip подключается к RealPay как **агент**: регистрирует турфирмы как мерчантов
и сам обслуживает вызовы RealPay за каждую из них.

См. также: [[Agent-API-RealPay]], [[Callback-API-RealPay]], [[Вопросы-к-RealPay]],
[[Vue-компонент-конструктора]] (платформа, на которой живёт easy-trip).

## Две стороны интеграции

| | Кто вызывает | Кто реализует | Авторизация |
|---|---|---|---|
| **Agent API** → [[Agent-API-RealPay]] | EasyTrip | RealPay | Bearer-токен из `auth/sign-in` |
| **Merchant API** → [[Callback-API-RealPay]] | RealPay | **EasyTrip** (5 эндпоинтов) | Basic, логин/пароль кассы |

Связывает их **касса**: при `merchant/v1/create` или `kassa/v1/create` мы передаём
`kassa.url`, `username`, `password`, и RealPay потом ходит на `${url}/info`,
`${url}/payment` и т.д. с Basic-авторизацией этими данными.

## Жизненный цикл турфирмы

```
Турфирма заполняет анкету в EasyTrip
  → ofd/v1/check-commitent   (зарегистрирована ли как комитент)
  → merchant/v1/create       (мерчант + владелец + счета + первая касса + договор)
Турфирма подписывает договор (EIMZO / FACE_ID / SMS …)
  → модерация RealPay → касса ACCEPTED
Касса видна клиентам как сервис в мобильном приложении RealPay
RealPay собирает оплаченные транзакции в payment order → перевод на р/с турфирмы
```

Изменения после подключения идут через **заявки** (`application`): отключить кассу,
расторгнуть договор, сменить счёт. Заявку рассматривает RealPay.

## Сквозной сценарий оплаты

1. Клиент в приложении RealPay выбирает кассу турфирмы и заполняет поля из `param_ins`
   (например, номер брони).
2. RealPay → `POST ${url}/info` `{amount, kassa_id, body}`. Мы проверяем бронь и сумму,
   возвращаем `additional` (показывается клиенту) и `ofd.items` (фискальный чек).
3. Клиент платит картой UZCARD/HUMO → `POST ${url}/payment` со `status: IN_PROGRESS`,
   затем **второй раз с тем же `transaction_id`** и `SUCCESS` или `ERROR`.
4. Неясный статус → `GET ${url}/check-status?transaction_id=…`.
   Не нашли у себя → строго `response_code: -99999`.
5. Отмена → `PUT ${url}/cancel`: клиенту возвращается вся сумма, комиссию RealPay
   оплачивает мерчант.
6. Сверка → `GET ${url}/reconciliation?from_date=…&to_date=…`.

> [!warning] Главный пробел
> Ни в одном документе нет API, чтобы **инициировать** оплату со стороны EasyTrip
> (ссылка, инвойс, checkout на сайте). Оплата стартует только из приложения RealPay.
> Типы касс `INVOICE`, `PAYMENT_ON_SPOT`, `REAL_GO` намекают, что другие сценарии есть,
> но они не описаны. Вопрос вынесен в [[Вопросы-к-RealPay]].

## Решения для агентской схемы (черновик)

### Одна точка входа на все кассы
`kassa.url` у всех касс указывает на EasyTrip, например
`https://easy-trip.com/endpoint/api/v1/real-pay` → RealPay вызывает
`…/real-pay/info`, `/payment`, `/check-status`, `/cancel`, `/reconciliation`.
Точный путь зависит от того, как конструктор роутит эндпоинты.

### Как понять, к какой турфирме пришёл запрос
`kassa_id` приходит только в `/info` и `/payment`. В `/check-status` и `/cancel` есть
только `transaction_id`, в `/reconciliation` — только период.

- `check-status` и `cancel` найдут кассу через нашу таблицу транзакций по `transaction_id`.
- **`reconciliation` без привязки к кассе отдаст транзакции всех турфирм сразу.**

Варианты:
1. **Уникальный Basic-логин на каждую кассу** → по логину находим кассу во всех
   5 вызовах. Заодно утечка одного пароля не открывает остальные кассы. *Рекомендую.*
2. Свой идентификатор в URL (`…/real-pay/{наш_id}/info`). Нужен роутинг с параметром
   пути в конструкторе. `kassa_id` от RealPay в URL не положить — его выдают только после создания.

Пароль кассы нам нужно только проверять, поэтому достаточно хранить хеш.

### Что должен уметь конструктор (проверить)
- принимать `PUT` (для `/cancel`);
- читать заголовок `Authorization`;
- отдавать свой JSON без обёртки платформы и всегда с HTTP 200;
- открывать эндпоинт без авторизации платформы (RealPay не пришлёт Bearer easy-trip);
- хранить секреты (логин/пароль агента) вне кода эндпоинта.

### Откуда `/info` берёт данные
`/info` находит бронь по полям из `body`, сверяет сумму и статус «не оплачено»,
возвращает:
- `additional` — то, что увидит клиент (ФИО, тур, даты);
- `ofd.items` — позиции чека: ИКПУ (`spic`), код упаковки, НДС,
  `commission_info` с ИНН/ПИНФЛ турфирмы-комитента.

Значит, у услуг турфирм нужно хранить ИКПУ, код упаковки и ставку НДС.
(Что комитент — именно турфирма, подтвердить у RealPay.)

### Сущности БД (черновик для обсуждения)
- **Турфирма ↔ мерчант RealPay**: `merchant_id` RealPay, `tin_or_pinfl`, статус
  регистрации, ссылка на договор и его статус.
- **Касса**: `kassa_id` (UUID от RealPay), турфирма, статус
  (`NEW/ACCEPTED/REJECTED/MODIFIED/DELETED`), Basic-логин (UNIQUE), хеш пароля,
  `min_amount`/`max_amount`.
- **Транзакция**: `transaction_id` от RealPay (**UNIQUE** — идемпотентность `/payment`),
  касса, бронь, `amount`, `payment_type`, статус, `external_id` (наш UUID),
  время в RealPay, время последнего изменения у нас.
- **Журнал входящих вызовов**: эндпоинт, тело запроса, ответ, время — для разбора
  спорных платежей.
- **Выплаты** (payment orders) — по желанию, подтягивать из Agent API для кабинета турфирмы.

### Статусы транзакции у нас
```
IN_PROGRESS → SUCCESS → CANCELLED
            ↘ ERROR
```
- Бронь считается оплаченной **только** на `SUCCESS`.
- Повторный вызов с тем же статусом → тот же ответ, без повторных действий.
- Может ли прийти `SUCCESS` после `ERROR` — вопрос к RealPay.

## План работ

1. Получение токена + общая обёртка вызовов Agent API с обработкой `code: -8`
   (см. [[Agent-API-RealPay#Токен]]).
2. Справочники `const/*`: формы бизнеса, категории, банк по МФО, типы полей.
3. Схема БД (см. выше).
4. Пять эндпоинтов для RealPay ([[Callback-API-RealPay]]).
5. Анкета турфирмы → `check-commitent` → `merchant/v1/create`; отслеживание договора
   и статуса кассы.
6. Кабинет турфирмы: выплаты и транзакции (`v1/payment/order/*`, `transactions/v1/get-detail`).
7. Сквозная проверка на stage.

## Безопасность

- Логин/пароль агента, токены RealPay и токены easy-trip **не хранить** в заметках,
  git и коде эндпоинтов. В присылаемых curl заменять токен на `<token>`.
- Ключ Redis для токена не должен совпадать с паролем (сейчас совпадает).
- Эндпоинты для RealPay: Basic-авторизация на каждом запросе, только HTTPS,
  по возможности белый список IP RealPay.
